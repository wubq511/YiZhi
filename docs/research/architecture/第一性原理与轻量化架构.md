# 第一性原理与轻量化架构

2026-10-27。针对 Robert 对选型依据、最优性与轻量化的追问。完成本研究后，Robert 已分别接受 Electron 宿主、TS／Node Worker 核心、每课 SQLite＋资源文件，见 [ADR-0002](../../adr/0002-electron-desktop-host.md)、[ADR-0003](../../adr/0003-typescript-node-worker-core.md)、[ADR-0004](../../adr/0004-sqlite-course-storage.md)；四项轻量化原则已进入 [PRODUCT.md](../../../PRODUCT.md#资源与轻量化)。正式应用尚未迁移。本文保留选择前的比较依据，区分事实、已接受设计与未完成验证。

## 1. 要优化的是什么

目标是在本地单人课程中持续阅读、编辑、核对原文和使用 Agent。优先保证已有内容可独立学习、输入与视野不被破坏、已确认保存的内容可恢复，再同时减少运行资源、分发负担与维护复杂度。“轻量”至少有安装体积、运行内存、CPU／能耗、磁盘增长和实现维护五个维度，不能拿其中一个替代其余。

| 必须满足的场景 | 推出的必要能力 | 不能直接推出的技术选择 |
| --- | --- | --- |
| 约 500 个丰富知识单元，但学生一次只读少量正文 | 轻量全图、按需呈现重正文；活动输入与选择保持稳定 | 不要求 500 份编辑器常驻，也不能由此决定 Electron 或 Tauri |
| 文字、公式、图形与 PDF 并排，学生连续输入 | 合适的内容模型、稳定编辑实例、明确手势归属；避免主界面线程长任务 | 不要求所有界面原生，也不证明固定 Chromium 才能满足 |
| 学生与 Agent 都会修改，且要求撤回和异常恢复 | 依据版本检查、修改与历史／回执一致提交 | 单人仍可能有并发意图；不需要多人协作基础设施 |
| 关学习窗口后任务继续，退出应用才停止 | 应用管理任务寿命，窗口只是学习入口 | 不要求开机守护进程、HTTP 服务或独立课程核心进程 |
| 新资料解析和生成可能耗时 | 计算与短提交分开、结果带依据版本、工作可停止和核对 | 不要求每个概念阶段一个常驻进程，也不要求某一语言覆盖全部阶段 |
| 课程自含资料与学习记录，可整体迁移 | 可移植课程格式、相对资源身份、一致备份／导出 | 不要求每份课程携带平台程序，也不要求所有资料装入数据库 |

这些输入来自 [PRODUCT.md](../../../PRODUCT.md) 和已确认的[架构规则](../../architecture/架构决策总览.md)。500 是本轮增长场景，不是容量硬限；完整内容与同时挂载的 DOM 是两个不同数量。

2026-10-27 只读计数：当前权威知识 JSON 为 **2,244,331 bytes、84 单元、1,215 个递归正文块**。在 `理论课／习题课／教材／笔记` 下按 PDF、图片、PPT 和 Word 扩展名统计到 **51 个文件、142,679,534 bytes**，其中教材 PDF 为 113,832,625 bytes。这是指定目录和扩展名的原始文件体量，非去重后的课程包、完整资源清单、解析产物或运行内存。它提示资料资源与结构化正文应分别考虑存储和加载，不支持任何框架性能结论。

## 2. 先消除不会增加学习收益的工作

以下设计不依赖具体桌面壳，通常比换语言更直接地减少本产品工作量。每项都保持已确认的学习行为。

Robert 明确要求记下其中四项：正文按阅读范围读取且完整离线可用；静态阅读、按需编辑与 PDF 按页／有界缓存；流式局部更新、实际修改历史与最新草稿；一个应用管理多课、工具按需启动。它们现已成为 [PRODUCT.md 的实现约束](../../../PRODUCT.md#资源与轻量化)，不只是研究建议；具体资源收益仍需按实现测量。

| 负担来源 | 推荐处理 | 必须保留的行为 |
| --- | --- | --- |
| 同时创建全部正文、公式与实验 | 全图保留定位所需结构，重内容按可见范围挂载；正在输入／选择的实例固定 | 全部内容仍已备齐、可离线取得；不能用卸载破坏光标或选择 |
| 每次流式更新重建整段对话、整板和整份课程 | 更新实际改变的块或消息尾部，订阅范围跟随对象；显示增量按帧合并 | 保存状态继续来自真实持久化，不能把画面已出现当已保存 |
| PDF／图片一次解码全部页，实验长期后台运转 | 原页和附近页按需渲染，复用有界缓存；实验按已确认规则离屏暂停 | 原文定位、页码、可返回状态不丢失 |
| 每个 token、按键都复制旧正文和整段历史 | 最新草稿覆盖自身；正式改动按变化对象记录；对话追加实际新增片段 | 已完成修改与学习对话可追溯，未完成输入可恢复 |
| 为所有课程、所有生产阶段常驻一套服务 | 只打开正在使用或有任务的课程；任务按需启动，有界并发 | 关窗后已有任务继续，重复打开不创建重复写者 |
| 为未来可能用到的 OCR／本地模型预装并常驻全部运行时 | 由选定工具的实际能力决定引入及启动时机 | 普通离线阅读编辑不依赖生成组件可用 |

这不是一份全部待建的优化清单。其中正文按需挂载、局部更新与历史粒度已有独立证据；PDF 缓存和正式编辑器仍需结合实际实现。已有[历史实验](../../../experiments/history-spike/README.md)在同一轨迹中把正文历史前后值从 30.24 MB 减到 1.86 MB，收益来自减少重复内容，不能归因于 SQLite 或外推为整课固定节省比例。

还需区分**按需挂载**和**按需读取**：当前 [main.jsx](../../../experiments/architecture-spike/src/main.jsx) 先加载完整 84 单元 fixture，再 `structuredClone` 成 500 单元；`managed` 减少的是重正文 DOM，全部正文对象仍留在内存。因此本轮宿主资源实验比较的是这份相同原型负载。正式设计可让全图只保留身份、标题、关系和布局，按阅读范围读取正文及必要缓冲；正在输入／选取的对象继续保留。没有测量这项改造的净内存收益，不填虚构百分比。

## 3. 从一次修改推导存储，而不是从数据库名称出发

例如 Agent 修正一条公式并同步调整依赖它的例题。系统必须在提交时核对读取依据和任务资格，然后让“新正文、对应的撤回材料、操作身份及结果回执”一起成立。否则会出现正文已变却无法撤回，或实际未保存却认为任务完成的状态。学生另写的一条无关笔记可以独立提交，不需要把全课内容和所有个人记录塞进同一巨大事务。

需要的是**小范围、原子的领域操作**。同一个存储容器并不意味着混合知识、布局和个人内容的含义，也不要求每次提交扫描整课。

| 可成立的方案 | 如何保证一致性 | 对本场景的实际代价与收益 |
| --- | --- | --- |
| 单个 JSON 同时包含当前状态、历史和任务 | 串行组织修改，完整写临时文件，再替换并处理持久化与恢复 | 静态或低频小文档直接明了；随着正文、历史和对话增长，小改动仍重写大部分状态，按需查询和格式演进由应用维护。不是做不到，而是产品需要持续更新的记录越来越多 |
| 不可变正文文件＋事务性版本指针／元数据 | 先完整发布新文件，再原子切换数据库中的引用；旧版本保留 | 正确且适合大型产物，是比“两个可写权威文件”更强的替代方案；大量小正文外置增加文件发布与资源回收工作，目前没有直接文件创作需求抵消这些成本 |
| SQLite 管理小型结构化内容和执行事实，大资源外置 | 一次短事务写相关当前值、历史、版本与回执；大资源先完整发布再登记引用 | 与本地单人、多个相关对象持续更新的负载匹配；需要应用 schema 升级、索引选择和一致备份，但无需另部署数据库服务 |
| 自建追加日志，再重放／物化当前状态 | 规定记录边界、截断恢复、版本、检查点及查询投影 | 可以实现同类保证；会自行承担成熟事务库已经解决的恢复和查询工作，当前没有特殊日志需求支持这笔复杂度 |

SQLite 官方将本地应用存储与桌面文件格式列为适用场景；它是嵌入式库，不意味着增加一个数据库服务器。[适用场景](https://www.sqlite.org/whentouse.html)。原子事务用于让一次操作完整成立或完整不成立；具体掉电持久性仍依赖配置和底层系统，不能以本轮进程退出测试代替。[原子提交](https://www.sqlite.org/atomiccommit.html)

因此选择 **SQLite＋课程内不可变大资源** 的依据是用较少自定义机制满足所需一致性和查询；Robert 已接受该选择。不是因为 500 单元很多、SQL 必然更快，或已经证明其他存储做不到。

最小组织是当前对象、正式变更与操作结果、最新草稿、任务／来源记录，以及确有查询用途的索引。正文可以按内容对象保存结构化载荷，不需要把每个富文本属性拆成 SQL 列；也不需要另放一份可编辑权威 JSON。界面按对象请求数据，搜索索引可重建。小资源是否内嵌由读取方式决定，不能把“所有二进制必须外置”变成无条件规则。

外置资料先完整写入并校验，再登记不可变引用；失败可能留下无引用资源，但不能让已提交内容指向未完成文件。读写中的 SQLite 也不总是只有一个磁盘文件：WAL 属于持久状态，备份必须通过一致导出或停止并正确关闭后复制，不能只取主数据库文件。[WAL 持久状态](https://www.sqlite.org/wal.html#the_wal_file)。这类边界仍需维护，没有“换成数据库就全部自动完成”的承诺。

## 4. 桌面壳需要比较两条完整路径

真正有竞争力的两条路径是 **Electron＋TypeScript／Node 核心** 与 **Tauri＋Rust 核心**，两边都可继续使用适合本产品的 Web 内容呈现与 SQLite。不能只比较 Electron 完整运行时与 Tauri 空壳，也不能默认 Tauri 必须另外捆绑 Node 后再评价它不轻。

| 取舍 | Electron＋TypeScript／Node | Tauri＋Rust |
| --- | --- | --- |
| 渲染环境 | 随应用交付 Chromium；引擎版本由产品选择，仍有 OS、输入法和 GPU 差异 | macOS WKWebView、Windows WebView2；需要维护两条引擎适配，WebView2 部署策略影响完整分发成本 |
| 日常课程核心 | 可复用宿主交付的 Node；SQLite 同步调用宜移出宿主事件线程 | Rust 核心可直接调用 SQLite，日常读写不必加入 Node／Python |
| 资源成本 | 要承担 Chromium／Node 分发与维护；进程和依赖应按实际需要配置 | 可复用系统 WebView，通常有更小的自带运行时负担；不能由安装包较小推出运行内存／CPU 必然较低 |
| 维护成本 | TS 消息合同和 UI 定义可以共用，输入数据仍需运行时校验 | Rust 与前端之间仍要维护类型／序列化边界；这是真实开发成本，不是功能不可行 |
| 应用效果与性能 | 固定引擎降低部分兼容变量，但不会自动减少 DOM／布局工作 | 相同页面可能同样满足要求；是否有难以修复的编辑差异要用真实场景判断 |

框架机制依据见[官方机制核查](../topics/轻量化架构机制核查.md)。现有 WK 选文差异可经一条明确 CSS 覆盖恢复，不能把该问题当成排除 Tauri 的充分理由。此前宿主实验只证明有限可行性，并非这两套完整架构的效果或资源排名。

**不能称 Electron 为符合轻量化目标的最优宿主。** 下方同条件测量给出了具体取舍：当前页面的动态路径上，Electron 的 rAF 长尾更稳定，WK 的动态 footprint 更低。以保住这一连续交互效果为前提，Robert 已接受 Electron，同时通过明确的轻量化设计控制其资源成本。若以后考虑重新选型，系统 WebView 能以可接受成本消除长停顿并保持资源收益，会是重新评估的有效证据；本轮不继续并行推进第二套宿主。固定引擎是辅助理由，不能替代效果与成本证据。

## 5. 逻辑核心不等于独立进程

课程核心负责的校验、提交与任务记录应保持清楚边界，但物理运行位置可以更轻。窗口关闭后任务继续，只要求这些逻辑不归 renderer 生命周期所有。

| 承载方式 | 优点 | 代价与边界 |
| --- | --- | --- |
| Electron 主进程内同步执行 | 没有额外消息和运行实例 | 磁盘与同步计算阻塞宿主事件循环；只作为负载对照，不用它承担不受控重活 |
| 主进程中的 Node Worker 线程 | 独立 JS 执行线程，可隔开同步 SQLite 和多数计算；关窗不必结束该线程 | 共享宿主进程的故障边界；线程间消息、生命周期和恢复仍需管理，原生崩溃不被隔离 |
| utility process | 可把课程核心的原生故障与宿主进程隔开；可以独立结束／重建 | 新进程、运行时与消息／恢复成本；本轮单人规模本身不足以证明必须采用 |

**因此撤回“默认一定采用独立课程核心进程”的强建议。** 经过下方比较，Robert 已选择宿主拥有的 TS／Node Worker 承载普通核心，为具体原生风险和重工具保留独立进程。没有真实隔离收益就不为分层额外分配进程。该原则也适用于其他宿主：逻辑模块可以共享宿主，确需隔离的工作再拆出。

## 6. 本轮补测与结论入口

本轮新增实验只补此前缺少的资源和承载证据，不重做正式应用：同一丰富页面的 Electron／WK 宿主成本，以及同一 Node SQLite 负载的主线程／Worker／utility process 比较。测量条件、失败和局限记录在各实验目录；尚未完成的数据不用于本文件结论。

### 同页面宿主资源：实际取舍已经可见

[资源实验](../../../experiments/desktop-resource-spike/README.md)在当前 M5／16 GiB macOS 机器上，以相同的 1000×700 CSS px、DPR 2、可见且聚焦状态，预定交替运行三对。每次 500 个 article、3 个重正文，动态阶段在约 8 秒内进行 16 次段落增长和按时间变化的相机移动。第一次失焦实验保留且不用于比较；修正测量条件后的三对全部满足条件，没有为了取得更好数字追加轮次。

| 相同原型场景 | Electron 40.10.6 | 系统 WKWebView |
| --- | ---: | ---: |
| 阅读阶段 footprint 中位数，三轮范围 | 247.87–251.60 MiB | 285.03–297.57 MiB |
| 正文增长＋相机阶段 footprint 中位数 | 609.74–615.48 MiB | 391.07–397.69 MiB |
| 同一动态阶段 rAF 回调间隔 P99 | 17.6–17.7 ms | 91–92 ms |
| 每轮大于 50ms 的 rAF 间隔 | 0 | 16 |
| 关窗后无任务、保留宿主的 footprint 中位数 | 86.85–89.44 MiB | 48.77–49.55 MiB |

footprint 是确认归属进程的 macOS 内核记账之和，包含压缩等语义，不等于独占整机 RAM；WindowServer 和共享系统服务没有分摊。关窗列没有运行课程后台核心。rAF 表示回调节奏，不是实际呈现帧、硬件 FPS 或物理输入延迟；不能从上述数字承诺整个产品的流畅度。

两端动态阶段 P95 都约 18ms，但 WK 的 16 次长间隔约占 4%，因此只看 P95 会隐藏这条实际差异。WK 的 CPU 占用也较低，不过它执行的相机回调更少，不能据此说在同等连续效果下更高效。没有做 profiler，不能把停顿归因于某一个 WebKit、布局或公式实现，也没有证明这种差异不可修复。

分发成本也需正面承认：本次固定版本的 Electron ZIP 为 **109.056 MiB**，展开 `Electron.app` 为 **259.018 MiB**，加 app 外许可等文件后的完整 release 为 **274.007 MiB**。这是引擎 release，不是正式产品安装包。最小 Swift WK 宿主未打包系统 WebKit，不能把其约 144KB 当成完整 Tauri 产品，更不能认为系统运行时成本为零。应用应独立安装并服务多门课程，避免每课复制这份运行环境。

这项实验给出的判断不是“某个壳总是更轻”：阅读与动态阶段的内存关系会反转，固定框架名称无法替代具体负载。选择 Electron 的一项依据是这条动态路径的回调长尾，同时接受并明确暴露约 212–222 MiB 的动态 footprint 差额；减少全正文常驻、无用重渲染和缓存仍是后续工作。

### 课程核心承载：线程是更轻的当前默认

[核心承载实验](../../../experiments/core-placement-spike/README.md)使用真实 Electron 40.10.6 内的 Node 24.15.0／SQLite 3.51.3，500 单元、7,732 个当前对象的同一预建数据库；三轮固定顺序，主线程／Worker／utility 各运行相同的有节奏和突发场景，共 18 场景、4,320 次保存。每场景 80 组双段落修改、80 次最新草稿保存、80 次消息追加，每条相同短事务按 `FULL` 提交。

| 指标 | 主线程对照 | Node Worker | utility process |
| --- | ---: | ---: | ---: |
| 打开相同数据库、预热后 host＋core footprint | 34.33–34.61 MiB | 40.41–40.50 MiB | 51.27–51.50 MiB |
| 保存后 host＋core footprint | 38.83–39.13 MiB | 45.47–45.86 MiB | 56.63–57.02 MiB |
| 有节奏场景保存确认 P95 | 0.820–0.935 ms | 0.999–1.098 ms | 0.510–1.179 ms |

此处没有学习 renderer，不是整应用内存；不能直接与上一表相加预测产品总量。测量用 Python 标准库读取内核记账，不代表产品需要 Python 核心。原生绑定的真实外键错误回滚、重复操作回执、结束承载后重开和独立最终内容校验均通过，18 个最终内容／历史／回执摘要一致；进程终止不等于断电或原生崩溃测试。

本负载的宿主定时器长尾接近空载噪声，主线程短调用也未出现严重阻塞；不能把结果说成“实验已证明 Worker 比主线程更快”，也不能说 utility 省去同步 SQL 阻塞就必然更优。Worker 的推荐来自把同步工作移离宿主事件线程的机制，并以约 6 MiB 的本次增量记账承担该边界；utility 在此基础上多约 11 MiB，没有观察到需要额外进程才能获得的短事务响应收益。其原生故障隔离价值仍然存在，只是当前课程核心尚无必须为它付费的已确认需求。

## 7. 已接受的组合与后续重点

当前已接受组合为 **Electron 宿主＋TypeScript／Node 课程核心 Worker＋每课 SQLite 与必要资源文件**。Robert 分别确认了宿主、核心承载和存储，不由其中一项推定另外两项，也不声称该组合全局最优。

- **Electron 已选定**：除了控制引擎版本，当前同页面动态负载的 rAF 长尾更稳定。与此同时，接受其分发体积、动态内存和关窗保留开销；Tauri 的比较保留为依据，没有被判为技术上不可行。
- **简化了核心的物理组织**：普通课程读写先用一个宿主拥有的 Worker，不为每课或每个阶段常驻进程。OCR、重解析或确需原生故障隔离的工具另行启动受管进程，等待模型响应不自动新增计算实例。
- **SQLite 的依据独立成立**：原子修改、历史与回执的共同提交可以减少自建恢复协议；一组修改只处理相关对象，大资源单独保存，不用关系型数据库名称替代领域设计。
- **轻量化的主要空间仍在工作量**：从按需挂载进一步到按需读取正文，编辑时才创建必要编辑实例，局部更新和有界资源缓存。线程相对 utility 节省的约 11 MiB，明显小于当前页面动态阶段的数百 MiB 变化，不能把进程调整当作所有性能问题的答案。

下一步最有价值的验证是把一个真实编辑目标、核心持久保存与撤销回执连成最小路径，并据真实页面剖析定位动态内存和长停顿的来源。物理输入和最终正式富文本仍需验证；现有资源测量不替代它们。不需要现在新增 CRDT、服务集群、独立图数据库或完整版本控制平台来达成这些目标。

最终选择应同时看实际输入效果、端到端响应、相关进程资源和实现维护成本。测试通过是所测边界内的证据；没有在当前环境做过的中文 IME、Windows、完整 PDF 工作区或多年历史不能被补成“已保证”。这也不要求先建设两个完整产品再做决定：补测应只针对能够改变取舍的关键差异。
