# 轻量化架构机制核查

2026-10-27。状态：有界机制研究，不构成框架选定、存储定案或 ADR。只核查官方文档与源码，没有安装运行时、运行基准或新增性能实测。

## 1. 结论与适用范围

**Electron＋TypeScript／Node＋SQLite 是能解释其适配理由的候选，但不是从课程学习需求唯一推出的组合，也没有证据证明它已经达到性能与资源目标。** 当前最直接的轻量化路径是减少不必要的加载、同时存活的复杂 UI 和后台计算，并按实际故障边界选择线程或进程；这不要求删减课程正文或学习能力。

三个关键结论：

1. **关窗后任务继续，不要求课程核心必须独立进程。** 主进程拥有的 Node worker 可以与学习窗口分离；`utilityProcess` 额外提供独立进程故障边界。二者都能移走同步调用对宿主事件循环的直接阻塞，但都不能自动保证任务恢复、低内存或退出清理正确。[Electron 应用生命周期](https://www.electronjs.org/docs/latest/api/app#event-window-all-closed)、[Node worker](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#class-worker)、[Electron utility process](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process)
2. **Tauri 复用系统 WebView，确实改变运行时的分发方式；小包体不能推出运行内存一定更小。** WebKit 与 WebView2 仍有内容执行、布局和多进程成本，外带 Node／Python 又会增加完整产品成本。两端引擎不同是兼容验证成本，不能直接推出必须 Electron。[Tauri WebView](https://v2.tauri.app/reference/webview-versions/)、[WebKit 架构](https://docs.webkit.org/Deep%20Dive/Architecture/WebKit2.html)、[WebView2 进程模型](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)
3. **每课 500 个丰富单元，不等于同时运行 500 份完整正文编辑器和实验。** 保留全部可离线读取的内容，同时按阅读范围挂载、静态显示非编辑公式、暂停离屏实验，有机制上的减负空间；能否保持输入、选文与返回现场的质量，取决于状态与加载设计，不能由换壳保证。[Chrome DOM 指南](https://developer.chrome.com/docs/lighthouse/performance/dom-size)、[MathLive 静态公式能力](https://mathlive.io/mathfield/guides/integration/#displaying-non-editable-formulas)、[React 状态寿命](https://react.dev/learn/preserving-and-resetting-state)

需求依据为 [PRODUCT.md](../../../PRODUCT.md) 和本轮明确要求：本地单人；每课约 500 个丰富单元；React DOM／MathLive；关闭学习窗口任务继续，明确退出应用任务停止；当前 macOS、Windows 后续必做。[运行交付与进程边界](../architecture/运行交付与进程边界.md)与[产品形态与运行架构比较](../architecture/产品形态与运行架构比较.md)只用于定位既有论证，本报告不把其中的推荐或历史实验当成新的机制证明。

下文用“**能力事实**”标记来源直接支持的行为，用“**需求推论**”标记设计判断，用“**反例／边界**”说明结论何时不成立。Node API 固定到 `v24.15.0`，Electron 关键源码固定到 `v40.10.6`，便于与既有上下文对照；这不是重新验证实际安装版本。Tauri 查阅 v2 文档，退出 API 用 `2.8.5` 文档示例；在线文档后续可能变化。

## 2. `worker_threads` 与 `utilityProcess`：隔离的对象不同

这里比较的是**由 Electron 主进程创建并管理的 Node `worker_threads`**，以及主进程创建的 `utilityProcess`。它们与页面 `Web Worker` 是不同入口，不能只用“worker”一词混称。

### 2.1 资源与执行机制

| 核查项 | 能力事实与直接来源 | 需求推论／不能推出的结论 |
| --- | --- | --- |
| Node worker 的执行环境 | Node 源码 `WorkerThreadData` 初始化自己的 `uv_loop_t` 并调用 `NewIsolate` 创建 V8 isolate。[固定版本源码](https://github.com/nodejs/node/blob/v24.15.0/src/node_worker.cc#L149-L179) | JS 堆与事件循环分开，但仍是同一 OS 进程、同一地址空间。不能写成“共享一个 JS 堆”，也不能写成“相当于独立进程”；新增 isolate、线程栈与模块实例仍有成本 |
| 同进程共享资源 | libuv 的线程池是全局的，供不同事件循环共用。[libuv 线程池](https://docs.libuv.org/en/v1.x/threadpool.html) | 把异步文件工作放到多个 Node worker，不会各自获得完全独立的 I/O 资源池。CPU、内存带宽和磁盘仍会竞争；增加线程不保证学习更流畅 |
| JS 数据传递 | Node worker 支持消息克隆、`ArrayBuffer` 转移和 `SharedArrayBuffer` 共享。[消息传递](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#portpostmessagevalue-transferlist) | 普通 JS 对象不是自动共享；共享地址空间也不等于课程对象无复制。小命令、局部结果和资源引用比每次复制全课更符合本负载 |
| Utility 的物理边界 | `utilityProcess` 创建具备 Node 与 MessagePort 的子进程；固定源码通过 Chromium `ServiceProcessHost::Launch` 启动。[API](https://www.electronjs.org/docs/latest/api/utility-process)、[启动源码](https://github.com/electron/electron/blob/v40.10.6/shell/browser/api/electron_api_utility_process.cc#L160-L176) | 它有独立地址空间与运行实例，并非另开完整 `BrowserWindow`。可以使用应用已交付的 Electron／Node 运行环境，无须仅为这一步另带一份独立 Node 安装；但子进程的堆、启动和通信仍有成本 |

**需求推论：**线程通常提供一个减少额外进程的组织机会；独立进程提供更强的故障边界。不能据此承诺某方案总内存更低：模块重复加载、数据复制、缓存和实际存活时间都会影响结果。本轮没有测量它们的净差额。

**能力事实与需求推论：**Node 官方主要把 worker 用于 CPU 密集 JS，并指出内置异步 I/O 通常更适合 I/O 工作。因此，等待云模型流式响应的“长任务”不因持续时间长就必须分配计算线程或独立进程；任务所有权、取消与持久记录仍需保留。下一节的同步 SQLite 调用是需要另行处理阻塞的情形，不能套用异步 I/O 的结论。[Node worker 用途](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#worker-threads)

### 2.2 JS 异常与原生崩溃必须分别判断

**能力事实：**Node worker 内未捕获的 JS 异常会终止该 worker，并在父侧 Worker 对象上产生 `'error'`；worker 内 `process.exit()` 只退出该线程。父侧必须处理 `'error'`：Node 的 EventEmitter 对无人监听的 `'error'` 会再次抛错，不能把“框架报告了线程错误”当成宿主已妥善恢复。[worker 错误事件](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#event-error)、[worker 内 API 差异](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#class-worker)、[EventEmitter 错误语义](https://nodejs.org/download/release/v24.15.0/docs/api/events.html#error-events)

**能力事实：**worker 的 `resourceLimits` 只限制部分 JS 引擎资源，不覆盖 `ArrayBuffer` 等外部数据；即使设置，进程仍可能因全局 OOM 中止。[Node 资源限制](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#new-workerfilename-options)

**需求推论：**由于 worker 与宿主同进程，原生代码的段错误、内存破坏或进程级 fatal abort 不具有线程隔离保证，可能带走宿主。独立 utility process 将此类直接故障限制在另一个进程地址空间，宿主可据退出事件处理失效；Electron 也明确把 crash-prone components 列为 utility 用途。这不隔离整机内存耗尽、磁盘故障、错误写库或宿主自身缺陷。[Electron utility 用途](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process)

**反例／边界：**“worker 中一抛 JS 异常就必然拖垮主进程”过度否定了线程能力；“worker 有独立 isolate，所以原生崩溃也不会影响主进程”则夸大了线程能力。是否值得独立进程，要看需要隔离哪种失效，而不是只看任务是否耗时。

`utilityProcess` 也不是自动恢复器。其 `'exit'` 表示子进程已结束；专用 `'error'` 事件描述 V8 不可继续的 fatal error，不能等同 Node Worker 的普通未捕获 JS 异常事件。固定版本源码还对 utility 中未处理的 Promise rejection 设置了 `warn-with-error-code`，因此也不能把所有 rejection 写成“必然退出”。任务成功、失败和可重试需由应用协议明确报告。[固定版 utility 事件定义](https://github.com/electron/electron/blob/v40.10.6/docs/api/utility-process.md#instance-events)、[固定版 NodeService 配置](https://github.com/electron/electron/blob/v40.10.6/shell/services/node/node_service.cc#L153-L170)

## 3. Node SQLite：同步调用需要移开阻塞，不自动需要独立进程

### 3.1 已确认的能力与版本边界

**能力事实：**Node `v24.15.0` 的 `node:sqlite` 标为 release candidate；`DatabaseSync` 与 `StatementSync` 的接口同步执行。`timeout` 是等待数据库锁的上限，不会把调用变成异步。`node:sqlite` 通过内置 binding 进入原生 SQLite 实现，因此“没有第三方 addon”等于“完全没有原生代码”也不成立。[固定版 SQLite API](https://nodejs.org/download/release/v24.15.0/docs/api/sqlite.html#class-databasesync)、[binding 入口](https://github.com/nodejs/node/blob/v24.15.0/lib/sqlite.js)、[原生实现](https://github.com/nodejs/node/blob/v24.15.0/src/node_sqlite.cc)

“SQLite 同步”在这里指选定 Node binding 的接口，不是所有 SQLite 绑定都只有同步 API。Electron 实际内置 Node 和所选绑定需随目标版本核对；开发机 Node 的 API 不能代替目标运行时。

### 3.2 三种放置方式能解决什么

| 放置方式 | 从机制可推出的结果 | 仍然存在的边界 |
| --- | --- | --- |
| Electron 主进程直接执行同步 SQL | SQL、锁等待与同步结果转换会占用调用线程；长操作可能阻塞窗口管理与宿主 IPC | 外层加 `async`、`Promise.resolve()` 或延迟一个 tick，只改变调度方式，不会把同步调用移到别的线程 |
| 主进程拥有的专用 Node worker 内执行 | 同步调用直接阻塞该 worker，而非主进程事件循环；主进程可用异步消息等待结果 | 该 worker 的取消、读写请求仍可能排队；原生故障属于同进程故障面，CPU／磁盘竞争没有消失 |
| Utility process 内执行 | 调用阻塞 utility 的执行线程，同时增加独立进程故障边界 | 不会让 SQL 本身更快，也不会自动隔离同一 utility 内其他任务的等待；多一份运行实例与进程间通信 |

上述是由同步接口与执行边界得出的**机制推论**，不是速度排名。依据：[Node 同步接口](https://nodejs.org/download/release/v24.15.0/docs/api/sqlite.html#class-databasesync)、[Electron 避免阻塞主进程](https://www.electronjs.org/docs/latest/tutorial/performance#3-blocking-the-main-process)、[worker 独立事件循环源码](https://github.com/nodejs/node/blob/v24.15.0/src/node_worker.cc#L149-L179)、[utility 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process)。

**需求推论：**本地单人课程需要的是一个明确的提交协调者和短事务，不需要因为学生编辑与 Agent 同时存在就建立多个独立写入服务。SQLite 官方将桌面应用文件格式列为适用场景；WAL 允许读写并行，但同一时刻仍只有一个写者。由此支持 SQLite 作为候选，并不决定 Node、Electron 或 WAL 必须采用。[SQLite 应用场景](https://www.sqlite.org/whentouse.html)、[WAL 并发](https://www.sqlite.org/wal.html#concurrency)

**反例／边界：**“单人只有 500 单元，SQL 一定足够短，可以直接放主进程”不能成立：正文长度、历史、资料索引、锁等待和迁移并不由单元数量约束。反过来，普通局部读写由专用 worker 串行执行、重解析在外部完成，已经可以移开宿主阻塞；“同步 API 所以必上独立核心进程”也不成立。同步长调用期间的即时取消不能只靠向同一事件循环发送一条取消消息实现。

## 4. 窗口寿命与主进程寿命：关窗继续是所有权问题

**能力事实：**Electron 主进程管理窗口和应用生命周期；`window-all-closed` 在所有窗口关闭时触发。不监听它时默认退出，监听后应用可控制是否退出；`Cmd+Q`／`app.quit()` 的退出路径又与该事件不同。不能直接照抄“非 macOS 最后一个窗口关闭就退出”的常见示例来满足本产品。[进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model#the-main-process)、[窗口全关事件](https://www.electronjs.org/docs/latest/api/app#event-window-all-closed)

| 工作归属 | 关闭学习窗口后的推论 | 明确退出时的要求 |
| --- | --- | --- |
| 页面自身、页面 Web Worker，或依赖该 renderer 存活的对象 | 不能作为关窗后继续的可靠任务拥有者；页面执行环境销毁后不能要求它继续协调任务 | UI 断开前后的未确认输入要有恢复归属 |
| 主进程拥有的 Node worker | 主进程保留运行、worker 未被终止时，可以跨学习窗口关闭继续工作；不需要把旧窗口隐藏着保活 | 封闭任务提交资格，完成已接收写入的处理，停止 worker，退出主进程 |
| 主进程监管的 utility／外部执行器 | 可以与窗口分开管理，重开窗口重新订阅同一任务 | 显式管理子进程与执行器，等待退出或按策略终止；不能只关闭订阅就宣称任务停止 |

表中为依据上述生命周期、[Node Worker](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html#class-worker)与[utility API](https://www.electronjs.org/docs/latest/api/utility-process)的**需求推论**。任务记录、写入资格和结果归属不应只放在学习窗口内，也不应因唯一 UI 消息端口关闭就被误判为任务完成。

**需求推论：**“后台任务”在当前需求中只表示不依赖学习窗口，不表示应用退出后仍存活的系统服务。正常退出应先阻止新提交、处理已接收数据、记录未完成状态，再结束受管执行；崩溃或强制结束时依靠运行期间的持久记录恢复，不能依赖最后一次退出回调。Electron 明确说明 Windows 关机／重启／注销时部分退出事件不会触发。[退出事件边界](https://www.electronjs.org/docs/latest/api/app#event-before-quit)

**能力事实与反例：**这个行为不专属 Electron。Tauri 2 的 `RunEvent::ExitRequested` 提供退出请求 API，`prevent_exit()` 可阻止相应退出；产品可区分关窗保留宿主与显式退出。该 API 有适用边界，不能拦截所有退出方式，更不提供任务持久化保证。[Tauri RunEvent](https://docs.rs/tauri/2.8.5/tauri/enum.RunEvent.html#variant.ExitRequested)、[ExitRequestApi](https://docs.rs/tauri/2.8.5/tauri/struct.ExitRequestApi.html#method.prevent_exit)

## 5. Tauri 2 的系统 WebView：省下的分发，仍需支付的运行成本

### 5.1 能确证的事实

| 能力事实 | 直接来源 | 对“轻量”的准确含义 |
| --- | --- | --- |
| macOS 使用系统 WKWebView，Windows 使用基于 Chromium 的 WebView2；macOS WebKit 随系统更新 | [Tauri WebView 版本](https://v2.tauri.app/reference/webview-versions/) | 应用可以复用目标系统的 WebView，不必为窗口自带同一套浏览器引擎；macOS 与 Windows 并不因此使用同一引擎 |
| WebKit 采用 UI、WebContent 与网络进程等边界；Tauri 自身也是多进程架构 | [WebKit 官方架构](https://docs.webkit.org/Deep%20Dive/Architecture/WebKit2.html)、[Tauri 进程模型](https://v2.tauri.app/concept/process-model/) | WKWebView 是完整 Web 内容执行环境，不是免运行时成本的 HTML 贴图；不能只统计 Rust 主进程内存 |
| WebView2 进程组包含 browser、一个或多个 renderer 及 GPU 等辅助进程；分组与用户数据目录有关 | [Microsoft 进程模型](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model) | 系统上已有 WebView2 文件，不等于应用不产生浏览器进程；共享安装不保证与所有别的应用共享同一运行进程 |
| Evergreen 可让应用共用已安装的 runtime 文件；缺失时仍需安装，另有离线与 Fixed Version 部署方式 | [Microsoft 分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)、[Tauri Windows 安装器](https://v2.tauri.app/distribute/windows-installer/) | 减少重复 runtime 分发是实际优势；缺运行时设备的完整安装成本仍需计入。固定 Windows runtime 也不会把 macOS WKWebView 变为 Chromium |
| Tauri 支持随包 sidecar，按目标平台／架构提供可执行文件 | [Tauri sidecar](https://v2.tauri.app/develop/sidecar/) | 保留 Node／Python 核心或工具时，要计算其运行时、依赖、进程和更新成本；若核心直接用 Rust，则不能强行把不存在的 Node 成本算进去 |

### 5.2 不能由这些事实推出的结论

以下均为**推论边界**，不是性能测试结果：

- **小安装包 ≠ 小运行内存。** 包体描述应用交付的文件；运行内存还包含宿主、Web 内容 JS／DOM、引擎、GPU／图片、后台核心、工具和缓存。系统组件承担了部分分发，不代表执行工作消失。
- **多进程 ≠ 必然比 Electron 更重。** 进程数量本身不能给出私有内存、共享页、资源寿命和同一负载的净成本；上述事实同样不能证明 Electron 更省。
- **跨引擎差异 ≠ 必须 Electron。** 它增加需要支持的行为与版本组合；若目标 WKWebView／WebView2 能正确完成中文 IME、公式编辑、选文、画板手势和恢复，就没有由引擎名称直接排除 Tauri 的理由。
- **统一 Chromium ≠ 消除平台差异。** Electron 缩小引擎与版本变量，但系统字体、输入法、GPU、窗口与退出仍有平台因素；它的收益是控制部分变量，不是所有设备自动同样流畅。

这些边界依据上一表的分发／进程事实和[Electron 固定 Chromium 的性能论述](https://www.electronjs.org/docs/latest/tutorial/performance#5-unnecessary-polyfills)。同场景内存比较应覆盖相关进程，区分共享与私有口径，避免直接累加可能重复计数的 RSS，也不能只比较应用主进程。Electron 的内存结构明确区分 `private` 与 `shared`；Node 在使用 worker 时，`process.memoryUsage().rss` 仍代表整个进程，不能把每个线程报告的 RSS 相加。这是后续测量口径建议，本次未执行。[Electron 内存字段](https://www.electronjs.org/docs/latest/api/structures/process-memory-info)、[Node 内存统计](https://nodejs.org/download/release/v24.15.0/docs/api/process.html#processmemoryusage)

**反例：**Tauri 小壳＋每次启动的 Node 核心＋常驻 Python 工具＋全量 MathLive 编辑器，并不能靠安装器小就证明省内存；Tauri Rust 核心＋按需页面与工具，则确有减少随包独立 runtime 的路径。反过来，一个控制了加载与后台工作的 Electron 产品，也可能比没有控制这些工作的系统 WebView 产品少做很多无用工作。这些是逻辑反例，不是现成产品的资源排名。

## 6. Electron 性能指南可确实消减什么

官方指南能指出可移除或延后的工作，没有承诺优化后一定快。以下“消减”指工作或资源的因果路径，不填写未经测量的节省比例。

| 官方能力／建议与直接来源 | 本需求下可落地的推论 | 不应混淆的边界 |
| --- | --- | --- |
| 检查模块依赖与加载代价；昂贵初始化按需执行。[指南 §1–2](https://www.electronjs.org/docs/latest/tutorial/performance#1-carelessly-including-modules) | 普通阅读不初始化 OCR、资料解析器、模型执行器和未打开的重面板；只在用到时加载工具与启动执行器 | 延迟加载减少当前工作与驻留机会，不一定减少安装包；当前可见公式需要的字体／样式不能拖到影响阅读 |
| 避免主进程阻塞、同步 IPC 和 renderer 长任务。[指南 §3–4](https://www.electronjs.org/docs/latest/tutorial/performance#3-blocking-the-main-process) | 同步 SQL、批量校验和重解析移离 UI／宿主事件循环；短且低优先级的 UI 工作才考虑空闲调度 | 移走执行位置改善响应机会，不等于总 CPU 减少；不能为每个小操作临时创建一个 worker／进程 |
| 删除已被目标引擎覆盖的 polyfill；打包代码；避免不必要网络资源。[指南 §5–7](https://www.electronjs.org/docs/latest/tutorial/performance#5-unnecessary-polyfills) | 对固定 Electron 目标构建；去除实际无用依赖；字体、MathLive 必需资产随包，本地读取 | 字体随包会增加分发内容；这换取离线确定性。打包本身不保证 tree shaking，也不能删掉真实需要的兼容代码 |
| 后台页面动画／定时器节流默认开启。[固定版 `backgroundThrottling`](https://github.com/electron/electron/blob/v40.10.6/docs/api/structures/web-preferences.md#L77-L83) | 保留合理节流，不为后台任务全局关闭页面节流；真正课程任务交由独立于窗口的核心执行 | 页内某个单元离开画板视口，不等于整个页面进入后台；不能指望这个开关自动暂停所有离屏实验 |
| 减少不必要 DOM 创建与重渲染。[Chrome DOM 指南](https://developer.chrome.com/docs/lighthouse/performance/dom-size) | 全课保留轻量身份／空间概览，只挂载阅读范围及必要缓冲区的复杂正文；Agent 局部变化不重建全课 | 500 是课程对象数，不是 DOM 数。画板需保持关系、位置、跳转与正文可达；不能用虚拟化删减学习内容 |
| MathLive 支持静态公式 HTML；生成后显示无需继续依赖编辑器库。[MathLive 集成指南](https://mathlive.io/mathfield/guides/integration/#displaying-non-editable-formulas) | 非编辑公式采用同一内容派生的静态呈现；开始编辑时创建 MathLive 编辑器，避免所有公式始终持有编辑实例 | 静态／编辑切换必须保持内容、选段锚点和显示一致；不能把正在输入的公式原地卸载再声称无损 |

“没有默认菜单就移除默认菜单”也是官方建议，但本产品需要常规编辑与退出入口，不能机械照搬为“删菜单即优化”。核心是去除实际不需要的工作。[指南 §8](https://www.electronjs.org/docs/latest/tutorial/performance#8-call-menusetapplicationmenunull-when-you-do-not-need-a-default-menu)

**效果保持条件，属于需求推论：**正文、推导、例题和题解仍预先存在本地；按需挂载只改变显示与执行时机。当前编辑、中文组合输入和有效选择要保持稳定；实验现场与未确认输入需先有独立状态归属，才能暂停或卸载。React 明确说明组件从树中移除会销毁其组件状态，所以“离屏直接卸载，回来 React 自然恢复”不成立。[React 状态与树的位置](https://react.dev/learn/preserving-and-resetting-state)

实验暂停、合并临时显示更新、限制解析并发、停止无人订阅的 UI 推送，属于据本产品需求延伸的策略，**不是 Electron 指南已经实现的功能**。只可合并过时预览，不能丢弃正式提交、保存确认或学生操作；后台计算暂停也不能误停用户明确要求关窗继续的有效任务。

**无法靠指南抹去的成本：**Electron 自带的 Chromium／Node 运行环境和其必要进程仍存在；线程、按需加载与打包不会将其变为系统 WebView。若未来硬性分发或常驻资源预算低于该方案能实现的水平，就需要重新评价宿主，不应继续用应用层优化掩盖结构成本。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

## 7. 从当前需求能推导到哪一步

| 判断 | 机制与需求支持的结论 | 可以推翻或限制它的反例 |
| --- | --- | --- |
| React DOM／MathLive 是否要求 Electron | 要求能承载其 Web 内容与交互的引擎；MathLive 是 Web component，并非 Electron 专用组件。[MathLive 官方项目](https://github.com/arnog/mathlive) | WKWebView 的真实输入／选择若出现代价不可接受的阻断问题，会增加固定 Chromium 的价值；“浏览器差异可能存在”本身还不是阻断证据 |
| TS／Node 是否有本质必要性 | Electron 已包含 Node，可减少再带另一常驻解释器的必要；课程协议与 UI 共享类型具有工程便利。它是条件收益，不是学习需求推导出的唯一语言。[Electron 主进程](https://www.electronjs.org/docs/latest/tutorial/process-model#the-main-process) | 若主要工具需要 Python，或核心用 Rust 能更直接实现且无需 Node，收益和维护成本会改变；前端用 TS 不要求后端同语言 |
| 独立课程核心进程是否必要 | 必须有独立于窗口的逻辑所有权；物理上 worker 与 utility 均有可行机制。前者隔离调用线程的阻塞，后者额外隔离进程级故障。[Node worker](https://nodejs.org/download/release/v24.15.0/docs/api/worker_threads.html)、[utility](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process) | 若明确要求原生核心崩溃后宿主继续，则主进程内 worker 不满足；若不需要该故障合同，不能只因关窗继续而强制增加进程 |
| SQLite 是否因规模而过重 | 本地应用文件与短事务符合其官方适用范围；引入 SQLite 不意味着要另起数据库服务器。[SQLite 适用场景](https://www.sqlite.org/whentouse.html) | 仅靠“500 单元”不能证明索引、历史查询与保存性能；选错绑定或把同步操作放 UI 线程仍会卡顿 |
| 能否保效果并轻量化 | 可以减少无用工作、减少同时存活的复杂实例，同时保留完整本地内容；这些机制不依赖删减课程。[DOM 指南](https://developer.chrome.com/docs/lighthouse/performance/dom-size)、[静态公式](https://mathlive.io/mathfield/guides/integration/#displaying-non-editable-formulas) | 为减内存破坏 IME、选文、笔记锚点、实验现场或保存确认，就不算保效果；实际延迟与内存净收益本轮未测 |

因此，既有“Electron＋TS／Node＋SQLite”推荐可以保留为待检验的工程候选，**不能提升为第一性原理的唯一答案**。其中可独立讨论的是：引擎版本控制是否值得自带运行时；课程核心需要线程还是进程故障边界；SQLite 绑定怎样避免阻塞；哪些重资源应按需存在。某一项成立，不自动使其他项成为必选。

本轮对两个常见论证的修正也应保留：**系统 WebView 小包体不能证明运行内存一定小；跨引擎维护成本也不能证明必须 Electron。** 当前没有资源预算或同负载测量足以作这种定案。
