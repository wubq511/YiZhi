# 历史语义与保存开销隔离实验

2026-10-27。**本轮 37 项检查通过，支持“变化对象的前后内容＋最新草稿”的最小历史方向。** 不需要为了本轮场景先引入差分压缩、全课周期快照或独立事件溯源系统。这不是正式应用实现，也没有选定数据库绑定或后端语言。

最明确的收益是减少重复历史内容。相同合成轨迹下，正文历史前后值从 **30.24 MB 降至 1.86 MB，减少约 93.85%**；数据库净增长从 30.99 MB 降至 2.95 MB。保存耗时有波动，第二轮变化块模式更慢，**不据此宣称整体应用始终更快**。

## 语义实验实际证明了什么

使用三个真实单元的结构和合成修改。`Ledger` 仅有当前对象、正式提交／前后值和最新草稿；初始对象作为一次基线记录，父子与顺序也在同一套数据中。前后值、回执和当前对象在一个 SQLite 事务中写入。它用于检验语义，未优化正常读写路径，也不作为生产 schema。

| 场景 | 实际检查 |
| --- | --- |
| 初始历史 | 真实嵌套块结构拆成对象后，重建的单元与原始值完全相等 |
| 同一任务连续改同一块 | A→B→C 按目标提交逆序撤回，得到 A，不把本次撤回自己的中间修订当冲突 |
| 后来个人内容 | 撤回任务后，另一块新增文本、个人笔记、布局和掌握状态均保留 |
| 同块再次编辑 | 学生把内容改走后又改回相同文字，仍因修订来源不同而保留当前，不靠值相等跳过冲突 |
| 原子修改组 | 组内一个块冲突时，不只撤回另一半，避免破坏组的一致性 |
| 学生操作的撤销／重做 | 调用方明确指定学生移动操作，后台 Agent 后续修改不被撤销；重做使用同一个逆操作原语 |
| 新增块及其笔记 | 撤回新增时恢复父级顺序，块退出当前内容；后写笔记与原版本仍可回查。没有实现待关联 UI |
| 恢复预览过期 | 预览后范围内新增对象，恢复拒绝；只核对旧对象版本不足以通过 |
| 恢复单元 | 默认恢复内容，保留笔记、布局、掌握状态和未完成公式草稿；其他单元草稿不会无端阻止恢复；显式选择布局才一起恢复 |
| 恢复后的反悔 | 恢复前状态继续可读，恢复本身能由同一套记录撤回 |
| 重复请求 | 撤回和恢复的同操作重试返回同一回执；恢复已改变当前修订后仍可补取回执 |
| 草稿与重开 | 连续 100 次草稿更新只维护该会话一行，不增加正式历史；迟到序号被拒绝；重开核对当前内容和最新草稿 |

这里的“学生撤销”验证的是**已选好目标后的数据操作**，不是键盘路由、编辑器撤销分组或原生 Undo 栈。实际按键证据另见[键盘撤销实验](../undo-input-spike/README.md)。

同操作回执重试在同连接内验证，不能扩大为本格式在崩溃后补回执已通过。另一子进程先确认草稿序号 2 已提交，再在序号 3 的未提交事务中 `os._exit(73)`；重开保留序号 2，没有把未提交替换当已保存。**本次异常退出只覆盖草稿**；之前的[通用事务实验](../storage-spike/README.md)有更广故障矩阵，但使用不同薄适配器。

## 成本比较如何保持可比

两种策略使用相同 SQLite 表结构、索引、当前内容写法、初始化数据和操作轨迹，唯一策略差别是正式正文历史行保存整单元，还是保存变化块。两边都读取、解析和写回同一整单元 JSON，也都准备同样的块序列化值；没有把当前对象拆分或减少其他校验的收益算到历史上。

负载是 **500 个单元副本，40 个活跃单元**，来源为 84 个真实单元的内容形状。每轮 1,600 次连续保存：

- 400 次正式正文组，每组修改两个单元的首个段落，共 800 个单元改动。
- 800 次最新草稿写入、200 次完成的布局移动、200 条合成对话片段追加。

副本只更换单元 ID，引用字段作为原始内容保留；本轮不检查这些复制对象之间的学科关系和证据是否成立。轨迹是确定性合成段落追加，**不是用户行为采样，也不是 500 个不同课程单元**。公式复杂编辑、图片／PDF、大二进制与块结构变更不在该成本轨迹中。

按整单元→变化块、变化块→整单元、整单元→变化块运行三对，预先固定顺序。每对验证 500 单元最终内容摘要相同，并核对 10 个单元在中间提交序号处的历史内容摘要相同。600 条正式操作记录包含 400 正文组与 200 布局操作；1,000 条历史行包含 800 个单元历史和 200 条布局历史，不能混用这些计数。

计时从读取当前数据之前开始，包含该次 JSON 处理、SQLite `FULL` 提交和循环内操作；不含 UI、IPC、正文呈现、课程语义校验、任务资格检查、真实执行器或外部资源发布。**成本计时没有调用上面的 Ledger 撤回／恢复实现**，不能作为正式课程命令端到端延迟。

## 结果与正确分母

以下 MB 为十进制。三对的逻辑字节和数据库大小一致，耗时按三轮范围列出。

| 指标 | 整单元历史 | 变化块历史 |
| --- | ---: | ---: |
| 正文历史前后值 UTF-8 字节 | 30,240,118 | 1,860,638 |
| 包括布局的历史前后值字节 | 30,246,472 | 1,866,992 |
| 初始化数据库 | 17,301,504 | 17,301,504 |
| checkpoint 后数据库净增长 | 30,986,240 | 2,945,024 |
| checkpoint 后数据库总大小 | 48,287,744 | 20,246,528 |
| 正文组保存 P50，ms | 0.909–0.931 | 0.763–0.835 |
| 正文组保存 P95，ms | 1.567–1.827 | 1.188–2.409 |
| 正文组保存最大值，ms | 8.407–17.035 | 2.870–20.926 |
| 每轮十次旧单元读取最大值，ms | 0.536–0.543 | 0.533–0.552 |

93.85% 指**本条轨迹的正文历史载荷减少**，不是整个数据库、整个课程或磁盘物理写入减少。数据库净增长减少约 90.50%，总大小减少约 58.07%；初始化含相同的当前值和基线，因此三者不同。文件长度和 WAL 长度也不是累计物理写入量，本轮没有测 I/O 写放大或 RSS。

中间轮变化块模式的 P95 和最大值更高，没有采集足够证据精确归因。不能抹掉该轮、只引用最快结果，或据三次短运行宣布交互性能已经改善。旧版读取在这条有限轨迹里没有明显额外量级成本，但每轮只有十个查询，且是刚写完数据库后的读取，不是冷启动或多年历史基准。

历史读取比较仅包含**固定结构内的段落追加**。语义实验检查过单个新增块的撤回，但没有测量任意增删、重排、拆合和嵌套结构变化后的历史读取成本。两者不能互相替代。

## 取舍与未覆盖范围

现有证据足以优先采用对象级前后值：先去掉全单元重复，就获得明确空间收益，没有必要立即增加压缩链。即使采用前后值，长段落反复编辑仍会增长；单次 93.85% 不能外推为固定节省比例或长期容量上限。

尚未覆盖：真正编辑器到课程核心的键盘撤销闭环、任务运行中停止再撤回、结构读取依赖闭包、复杂拆合锚点、语义关系／实验配置校验、整课代际恢复、恢复时异常退出、磁盘损坏／满盘、资源迁移、格式升级、多连接竞争和 Windows。这些不能因一个薄适配器通过就写成正式功能；也不要求现在为了补齐清单建设全部机制。

实测环境为 macOS 27.0.1 / arm64、Python 3.14.6、SQLite 3.53.3。实际设置为 WAL、`synchronous=FULL`、4096 页字节、`wal_autocheckpoint=1000`，`fullfsync=0`、`checkpoint_fullfsync=0`。进程退出测试不证明掉电持久性，Python 标准库成功也不代替最终 Electron／其他宿主绑定验证。

下一步应接通一个真实编辑目标、保存和撤销回执，检查从快捷键到持久状态的闭环；保留期限和压缩策略暂不拍脑袋定值。这里的独立实验可以保留为证据，不直接搬入正式应用充当历史引擎。
