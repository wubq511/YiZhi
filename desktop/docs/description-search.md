# Agent description search (T20)

The explicit “按记忆线索查找（Agent）” disclosure extends the existing offline search panel. Ordinary keyword/alias/symbol input does not invoke description inference. Opening the disclosure checks the installed CLI and actual model catalog; only “用描述查找已有内容” starts remote search planning. Availability of the CLI/catalog is shown separately from an actual successful request. Missing CLI, offline state, provider failure and the remote deadline leave the independent T15 input usable. There is no model download or whole-course rebuild in the description runtime.

`window.yizhi.description` exposes `status/start/get/cancel` through the incumbent restricted main-frame IPC. `DescriptionRuntime` belongs to the host and uses the same existing CourseService; it creates no second course writer or Worker. `start` returns a request identity immediately after cheap course-session validation, before model work. Scopes, description and selected model are fixed for that request. Exact retries share that request; changing its input under the same identity rejects. One active request per course is admitted. Completed/failed/cancelled records and query proofs remain in bounded host memory (latest eight requests); they are not a new permanent learning transcript or persisted task/resume mechanism.

The real app-server adapter reuses T16's `detectExecutor`, reduced-PATH `executorEnv`, `AppServerRPC`, generated discriminated function-tool types and `READ_ONLY_CONFIG`. Each description gets a new `ephemeral:true` thread with `runtimeWorkspaceRoots:[]`, an empty course-external cwd, read-only sandbox and approvalPolicy never. Shell/unified exec/apply patch/apps/plugins/MCP/hooks/memories/multi-agent/web/image capabilities remain disabled. Existing CLI authentication is used in place. No API keys/auth files are copied. The process uses shell:false and is closed/reaped when the request finishes, fails, stops or the host exits. It never borrows the QA conversation, selected target, history or unsent composer.

Exactly two model tools exist:

- `yizhi_search({query})`: up to four literal queries, with fixed submitted scopes, through actual `CourseService.search.query`, eight hits per query. It neither rewrites the authority nor rebuilds the index. Tool replies omit whole-field text; bounded actual excerpts, identity/version/location and query coverage remain.
- `yizhi_select_search_hits({hitIds})`: choose/order up to twelve host-issued IDs from those actual query replies. Unknown IDs, duplicates, extra fields such as a model-provided quote, and other tools reject. Maximum twelve unique tool calls and a 90s remote deadline bound work. Stop revokes publication immediately and closes that description's process; no implicit retry/resume occurs.

The host derives a hit identity by hashing actual scope/entity/version/field/block/page/projection/range. It retains the canonical SearchHit and records query ID, exact executed query, tool call ID and original rank for every occurrence. The final selection tool call records selected IDs/order. A successful terminal turn is required before any enhanced hit is published; each selected hit is revalidated with actual `search.locate`. Changed versions are separately rejected. Generated final prose/deltas, invented explanations/quotes and inferred objects are never search projections. The UI's basis is these actual query/selection facts, not model-authored justification passed off as course text.

Query proofs retain T15's pending/incomplete/truncated, index-error, unreadable-original, no-text-page and unavailable-body states. Checked-range no-hit differs from incomplete search or unreadable evidence. An empty model selection after nonempty actual queries is also labelled separately. Every visible hit uses the same versioned card, canonical locator and return-scene handling as offline search.

Readonly search/return must preserve course body, review state and unsent conversation text **and target**. Only real mouse/key selection events originating in the selected reading article can update a QA draft target; clicking search/header controls cannot recycle a programmatic search highlight as a new question. The T16 UI fixture dispatches its selection event on the actual paragraph while retaining the same target/citation/Undo/reopen assertions. PM paragraph search highlights use editor-owned Decorations, not mutable DOM attributes that PM can discard. They affect neither content nor Undo history. Narrow search takes precedence over the prior directory when resizing and restores focus on close.

Validation is at public CourseService + actual app-server protocol and actual Electron IPC seams. `tests/description-search.test.ts` uses the controlled CLI protocol peer with real Worker/SQLite/query results. `tests/description-search.spec.ts` covers actual 1024×688/700×700 UI, unchanged drafts, offline/missing CLI and real locator return. `tests/description-search-real.spec.ts` is the separately required installed-CLI acceptance: run with `YIZHI_REAL_DESCRIPTION=1`, optionally `YIZHI_DESCRIPTION_COURSE` pointing to a previously verified stopped candidate which is copied into a disposable course. Its evidence captures actual CLI/model/thread/turn/query/hit IDs/basis, current canonical locations, unchanged body/graph/review/conversations and offline/missing-CLI fallback after reopen. Controlled peers never substitute for that real request.

All local UI runs use `python3 /tmp/yizhi-implement-gFFkA7/run-ui-serial.py npx playwright test ...`; resize only after workspace readiness, at the same actual size after reopen. No old17-query benchmark or new T15 full-index acceptance is needed. Existing source extraction/OCR limits, exact literal math distinctions and explicit pending coverage remain T15 contracts.

Protocol reference: [official Codex app-server documentation](https://learn.chatgpt.com/docs/app-server). This feature adds no T17 mutation, T18 resume/recovery or learning question submission.
